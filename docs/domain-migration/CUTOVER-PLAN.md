تاريخ الفحص: 24 أكتوبر 2026. **لم يُنقل الدومين، ولم يتغير DNS أو SSL أو إعداد إعلانات. لا يجوز دمج هذا الفرع أو ترقيته إلى Production قبل اعتماد النقل.** لم يُحذف مشروع أو مستودع.

## ما أثبته الفحص

الدومين العام يعيد 200 عبر HTTPS، وHTML يحمل `generator=Hostinger AI Builder` وأصول `zyrosite.com`. نسخة www تعود إلى الدومين الأساسي. Vercel يتعرف على الدومين كـ external وverified=true ضمن فريق EL-miraj، لكن هذا يثبت وجوده في الحساب، ولا يثبت أن زواره يصلون إلى مشروع Vercel.

خوادم الأسماء هي `ns1.dns-parking.com` و`ns2.dns-parking.com`. يشير www إلى `www.salemdztube.com.cdn.hstgr.net`، والبريد يستخدم MX لدى Hostinger. [لقطة السجلات العامة](dns-before.json) محفوظة. لم نغيّر Nameservers أو MX أو TXT.

لذلك لا تكفي افتراضياً إعادة إسناد مشروع Vercel لنقل الزيارات. يلزم التحقق من سجلات استضافة الويب لدى مزود DNS الفعلي قبل أي كتابة. قد تكون القيم العامة تسطيحاً لسجل ALIAS؛ ليست بديلاً عن مراجعة منطقة DNS القابلة للتحرير.

قراءة تفاصيل المشاريع والـaliases في Vercel أعادت 404، وقائمتها خالية ضمن الاتصال المتاح. لم يُحدّد مشروع قديم بالتخمين. مصدر الموقع القديم القابل للتحرير، وأي ارتباط فعلي له بمشروع Vercel، ما زالا بحاجة إلى تحقق.

يوجد مشروعان يبنيان مستودع GitHub نفسه وفق تعليقات Vercel في PR5: `salem-dztube-website` و`salem-dztube-website-ab5g`. المستخدم حدد الثاني، بينما عنوان الموقع الجديد المقدم هو `salem-dztube-website.vercel.app`. يجب قراءة Domains وGit وProduction للمشروعين وتثبيت الهدف قبل الإسناد.

أحدث main عند بدء العمل هو `13f07c594c5a3dc2aff940914bc63266eb6206ea`. أُنشئ فرع رجوع للموقع الجديد: `backup/before-domain-migration-20261024`. PR5 للمرحلة السادسة منفصل وغير مدمج. فرع النقل مبني على main ولا يلغي PR5؛ إذا اعتُمد PR5 أولاً، تُحل تعارضات build/robots ويعاد الاختبار قبل الدمج.

## التعديلات البرمجية الجاهزة

- استُخدم `SITE=https://salemdztube.com` في الفرع فقط، مع تحديث الرئيسية وrobots. يشمل ذلك Canonical وOG وSchema وصور المشاركة وروابط مشاركة المقالات. الروابط النسبية وSupabase والصور الحالية باقية.
- يستعمل البناء SITE لإنتاج robots، ويولّد صفحة الفيديوهات والمقدمة المحفوظة، ويمنع فهرسة صفحات Preview الجديدة.
- أضيفت تحويلات 301 دقيقة إلى vercel.json ومحاكاة محلية مطابقة، و410 للمتجر. لم تتغير Root Directory أو أوامر البناء أو قواعد المقالات الحالية.
- أضيف `scripts/check-domain.mjs`: اختبار قراءة فقط للمسارات وCanonical وSitemap ومقال منشور و301 و410 و404. لا يستبدل فحص الهاتف أو DNS وSSL.
- لم تُضف تحويلاً شاملاً من عنوان vercel.app قبل النقل؛ سيعيد الزوار إلى المحتوى القديم حالياً. بعد نجاح الوجهة الرسمية، يجهز تحويل مقيد باسم Host يحفظ المسار والاستعلام، دون التأثير في Preview.

## المتطلبات قبل طلب موافقة التحويل النهائي

1. إتاحة المشروعين لاتصال Vercel، وقراءة Production وGit وRoot Directory والدومينات. يجب تحديد إن كان هناك مشروع قديم مرتبط بالدومين أم مجرد سجل في الحساب.
2. تسجيل معرفات Project وDeployment والدومينات والتحويلات الحالية، والاحتفاظ بمصدر الموقع القديم ونسخته القابلة للتحرير. جرد HTML العام ليس نسخة مستودع كاملة.
3. الوصول المصرح به إلى DNS الفعلية وحفظ تصدير المنطقة أو السجلات التي ستتغير وTTL قبيل التنفيذ. لم تتوفر خدمة Hostinger DNS متصلة في الأدوات؛ إضافة Hostinger Mail لا تدير DNS.
4. الحصول على القيم المطلوبة من Vercel للمشروع المستهدف نفسه. لا يستخدم IP من مثال عام ولا تُكتب قيمة مفترضة.
5. معاينة مرشحة Ready وفحص فعلي على Vercel للرئيسية والمقالات والإدارة والسياسات والصور والفيديو وSEO والتحويلات. المعاينة المحمية تحتاج صلاحية اتصال، وليس تعطيل الحماية.
6. Supabase: دخول كلمة المرور الحالي لا يستعمل redirectTo، فلا يتطلب نقل الدومين إعادة إنشاء جداول أو RLS. قبل استعمال استعادة كلمة مرور أو OAuth، تُراجع Auth → URL Configuration وتضاف المسارات الدقيقة اللازمة للدومين الرسمي مع إبقاء المستخدمة. لم تتوفر أداة لقراءة Auth config، ولم يُعدّل من التخمين.
7. عرض المصدر القديم والهدف النهائي وقيم DNS المقترحة ونتائج الاختبارات وخطة الرجوع. **موافقة سالم الصريحة مطلوبة قبل الإسناد النهائي وكتابة DNS ودمج نسخة النقل.**

## التنفيذ بعد الموافقة فقط

حضّر Production المرشح من المراجعة المعتمدة مع خطة إسناد متزامنة، ولا تجعل نشره على الدومين العام خطوة سابقة للاختبارات. تحقق أن منع الفهرسة خاص بـPreview.

إذا ثبت ارتباط الدومين بمشروع Vercel آخر، استخدم أداة نقل Project Domain الرسمية بعد مراجعة عملية API الحالية. لا تحذف المشروع ولا تنقل ملكية الفريق ولا تعيد شراء الدومين. اربط apex وwww في المشروع المعتمد، واضبط www → apex مع حفظ المسار والاستعلام.

إن أكد الفحص حاجة DNS، غيّر فقط سجلات الويب اللازمة في Hostinger بالقيم التي أعادها Vercel. أبق NS وMX وSPF وDKIM وDMARC وسائر الخدمات. راجع AAAA القديم أيضاً؛ لا يُترك ليعيد زوار IPv6 إلى الموقع القديم عندما يصبح A إلى Vercel. استبدل أو أزل سجل الويب المتعارض فقط بعد حفظ حالته السابقة.

تحقق من DNS عبر أكثر من محلل، وشهادة HTTPS للاسمين، والتحويل من HTTP إلى HTTPS ومن www إلى apex دون حلقة، ثم شغّل الاختبارات مباشرة. قبول طلب API ليس إثباتاً لانتشار DNS أو جاهزية الشهادة. احتفظ بالموقع القديم وعنوان معاينته الموثق، وأضف تحويل عنوان vercel.app بعد نجاح الوجهة الجديدة.

## الرجوع عند فشل أساسي

- إذا كان الخلل برمجياً والإسناد صحيحاً، أعد Deployment المختبر السابق حسب نوع الخلل. مجرد تغيير SITE للخلف لا يعيد محتوى Hostinger.
- إذا فشل الانتقال من Hostinger إلى Vercel، أعد سجلات الويب المعدلة فقط إلى نسخة المنطقة المحفوظة قبيل العملية، بما فيها AAAA وwww. لا تغيّر خوادم الأسماء أو البريد. القيم العامة المرجعية محفوظة، لكن الأصل هو التكوين القابل للتحرير المسجل قبيل التنفيذ.
- إذا كان النقل فعلياً بين مشروعين في Vercel، أعد Project Domain وwww وتحويلاتها إلى المشروع القديم ومعرف Production المسجل.
- افحص رجوع الموقع القديم دون افتراض أن DNS وcache يعودان فوراً. لا تحذف أي نسخة قديمة بعد النقل.

## Search Console وAdSense

Search Console غير متصلة؛ لم تُعرف الصفحات المفهرسة أو الزيارات، ولم تُرسل Sitemap. بقاء الاسم وHTTPS نفسيهما لا يستدعي Change of Address تلقائياً. تُراجع الفهرسة وCanonical و301 وSitemap بعد النقل.

وُجد سكربت AdSense فعلي واحد للمعرّف المقدم في HTML القديم، بينما ads.txt القديم يعيد 404. هذا لا يثبت قبول الدومين أو تفعيل Auto ads. الحساب غير متصل؛ حالة Sites والمراجعة والسياسات غير متحققة. النسخة الجديدة تبقى verification-only مع ads.txt الصحيح ودون SDK. يجب عرض اختلاف سلوك الإعلانات على المالك قبل اعتماد النقل. لم تتغير إعدادات Google ولم تُطلب مراجعة جديدة.
